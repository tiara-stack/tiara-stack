# State and consumer isolation for selective development previews

Research for [TIA-223](https://linear.app/tiara-stack/issue/TIA-223), under [TIA-220](https://linear.app/tiara-stack/issue/TIA-220). Analysis date: 2026-09-18. Repository baseline: `0459b7a95a39cee283f608a6e829da02b827ebd4`.

## Finding

Concurrent web previews can reuse compatible development services. A changed db-server needs its own Zero callback path to exercise changed query and mutation code. A changed workflow runner cannot safely become an independently selected preview merely by receiving a new HTTP address: its SQL cluster membership and durable command store still belong to the shared consumer pool. For workflow and bot changes, an explicit shared owner or a separate execution/state boundary is required. These are recommendations for the later human decision, not approvals to change shared services. [R1][R2][R3][R4]

Use the existing State Plane vocabulary: Authoritative Application State, Operational State and Replicated State. Shared compatible authoritative rows do not imply that two versions should share consumers, sessions, capability references or projections. The Compose isolation statements in the baseline `CONTEXT.md` are historical and were not used to determine current Compose behavior. This investigation concerns development previews only and excludes sheet-formulas and vibecord. [R0]

The checkout catalog and installed dependency manifest agree on `effect@4.0.0-beta.67`; this version includes Cluster and Workflow under `effect/unstable`. Both the installed Zero package and the Helm default image are `1.5.0`. Source from these installed packages was inspected read-only in the parent's `node_modules/.pnpm`. | Workflow cluster storage | `sheet_workflows` feeds both SQL message and runner storage. Effect creates prefixed messages/replies/migration tables and runner/lock tables. Runner identity is its address, while shard ownership uses SQL locks. | A new port or runner address creates another member of the same cluster. Use a separate database, or consistently separate the complete cluster prefix. Prefix changes also imply fresh cluster migration state. [R1][R2][E1][E2] |
| Workflow command and run records | All roles receive `workflowStoreLayer({tablePrefix: "sheet_db"})`. Ordinary runners start command dispatch and run reconciliation. Claims use `FOR UPDATE ... SKIP LOCKED` and lease fencing on the shared command table. | Cluster prefix isolation alone is insufficient: a preview dispatcher can still claim shared commands and publish shared run outcomes. Keep command/run store and cluster namespace aligned. Current generated Zero mapping and application schema name `sheet_db_workflow_run`; dynamically changing prefixes requires coordinated persistence, schema and observation changes, not an environment-only switch. A separate database preserves existing table names. [R1][R3][R7][R8] |
| Workflow shard groups | Ordinary runners own `dispatch` and `autoCheckin`; browser runners own `browser`, with 300 shards per group. Registrations and annotations use those groups. | Ordinary versus browser is a role split, not a checkout split. A second compatible runner can process shared jobs. Group names alone do not isolate command claims or durable records. Routing one request to a preview API does not guarantee a preview runner executes it. [R1][R9] |
| Runner health | `RunnerHealth.layerK8s` looks up advertised `address.host` in a map keyed by pod IP. Missing entries are unhealthy; Kubernetes API failures are treated as healthy. | A native runner hostname is not represented by the healthy pod set. Connectivity alone does not fix this. Native mode needs a deliberately compatible health implementation across its fleet; cluster reload is a viable constraint-driven fallback. Do not depend on API failures to keep a native runner healthy. [E3][E4] |
| API-owned autonomous triggers | API and combined roles start auto-checkin and role-cleanup scheduling. Sweep identities are stable by kind and hour bucket. Smoke startup work is separately configurable. | The API is not passive. Same-state, same-contract sweep enqueues have stable identities, so duplicate API timers do not by themselves prove duplicate external writes. Different isolated stores lose that common deduplication boundary, and changed identity/behavior can diverge. Require one timer owner or explicit preview task controls; no general task-disable switch was found in this startup path. [R3][R9][R10] |
| Application schema | `DBService` runs `PgMigrator.run` before creating its application client. There is no skip-migrations branch in this service. | Starting changed db-server code can migrate the shared database before a test request. Share only when the exact migration set and old/new consumers are compatible. Incompatible changes need a separate database and matching Zero/consumer services. A reverse proxy does not protect schema. [R4][R8] |
| Zero metadata and replicated state | Zero 1.5.0 supports `ZERO_APP_ID`, default `zero`. App and shard metadata live upstream; CVR and CDC use app/shard schemas. CVR tracks client views, CDC stores recent replication changes, and SQLite is rebuildable. | A preview can use a distinct app ID plus its own replica file and callback pair while retaining compatible application tables. Separate CVR/change database instances are not intrinsically necessary because the app namespaces them. This still writes metadata to upstream and requires replication/publication privileges. Never reuse a live replica file or assume a different port creates a different app. [Z1] |
| Zero callbacks | Helm sets one query URL and one mutate URL to the shared db-server. Authorization is forwarded; cookies are disabled. Zero's mutation processing receives app/schema identity in callback query parameters. | Web-to-Zero routing alone will still execute the shared callback implementation. For concurrent changed db-server behavior, use a preview Zero instance with callbacks to that server, or implement and prove a compatible callback routing mechanism. The current chart does not expose per-preview app IDs/callback selection. An isolated Zero app does not isolate application rows or incompatible upstream DDL. [R6][Z2] |
| Bot operational identity | Redis caches use `discord:${clientId}:`. Capability records use that provided storage and an encryption secret. Bot main starts commands, event consumers, buttons and HTTP routes together. | Same client ID/Redis means shared cache and capability namespace. Changing only encryption secret makes existing encrypted references unreadable. A changed full bot is not an HTTP-only preview and can consume gateway events. Recommend one owner per development Discord identity, or a dedicated development application/resource set with matching workflow callback, Redis namespace and credential configuration. Exact duplicate-gateway delivery behavior was not tested. [R11][R12][R13] |
| Auth | Auth has PostgreSQL-backed identity/session state and configurable Redis base. Its base URL is the issuer, with configured audience/trusted-origin and token-exchange constraints. | Unchanged shared auth can serve compatible previews if their origin/audience contract is admitted. An auth implementation/schema change couples its database, Redis base, issuer/JWKS and callers; separate hostnames alone do not separate identities or sessions. Credential configuration must remain development-only. No tokens were issued. [R14] |
| Search index | Web is the query consumer. Indexing uses configured index UID and admin credentials; incremental mode deletes stale documents and rebuild swaps the target index. | Share unchanged search with search-only credentials. Docs/index changes require a preview index UID and matching query configuration, or one coordinated shared index owner. A separate index can use the same Meilisearch server if credentials permit that exact scope. Re-indexing the shared UID affects other previews. [R15] |

## Scenarios to settle with the developer

1. Two web worktrees alter layout and share current backend contracts. Keep shared State Plane; verify each origin can authenticate and query, and label writes as shared development writes.
2. A worktree changes a Zero query with no migration. Use a distinct Zero app and callback pair, retaining upstream rows. Demonstrate that only preview callbacks execute for preview requests. The shared cache callback remains unchanged.
3. A worktree removes or reinterprets a column. Use an isolated upstream database and matching consumers, or explicitly coordinate a single shared schema owner after compatibility evidence. An isolated Zero cache cannot make this schema change private.
4. A runner changes a durable action. Choose either coordinated ownership of the shared execution fleet or an isolated command/run/cluster set. Merely adding a runner cannot guarantee that a preview request reaches it. Existing pending work and pinned action/definition compatibility must be considered before any replacement.
5. A preview enables autonomous work in an isolated database but retains shared Discord and Sheets targets. Independent idempotency stores can perform the same real action twice. Require dedicated external targets, disabled autonomous triggers or a deliberately owned integration check. Database isolation is not external-effect isolation.
6. A bot handler changes. Decide whether to temporarily own the existing development bot identity or obtain a dedicated development identity and target resources. This research authorizes neither choice.

Scenarios 1–6 follow the constraints above and are proposed acceptance cases, not completed experiments.

## Missing verification and acceptance evidence

Implementation must establish the deployed image digests/package versions, actual non-secret database identities and publication/replication configuration, pending durable work, callback targets, preview auth origins, available development identities, and native runner health/reachability. No credentials or shared runtime state were inspected in this task. The checkout proves intended configuration, not the currently deployed state.

A later authorized experiment should use synthetic development work with no Discord/Sheets effects: prove a workflow submission and observation stay in the selected cluster/store; prove unchanged shared commands are never claimed by an isolated runner; restart the selected runner and check recovery; exercise distinct Zero apps against compatible rows and prove callback identity; verify incompatible schemas never start against the shared database; prove preview search updates leave the shared index unchanged. External action checks need named development resources and explicit authorization. No migrations, resets, seeds, deployments or external calls were performed here.
